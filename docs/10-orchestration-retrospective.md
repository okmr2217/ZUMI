## うまくいったこと

1. **理由つきの docs と「2026/11 確定」の記録**
   - 要件に「なぜそう設計したか」が書いてあったので、作業セッションは迷ったときに docs の意図から判断できた。
   - 作業中に決まったことも、その場で docs に書き戻した（境界ルール、前週比、シェア画像の運用など）。後から起動したセッションは、前のセッションの判断を docs から読めた。
   - 指揮役のコンテキストが一度要約されたときも、CLAUDE.md の「現在の進捗」と docs から状況をすぐに取り戻せた。
2. **依存関係つきの分割表（CLAUDE.md の S1〜S11）**
   - 着手条件・推奨エフォート・触る範囲が先に決まっていたので、並行で起動できるものを機械的に選べた。
   - S1（土台）を先に直列で通したことで、型・定数・テスト基盤を後続が共有できた。
3. **スキーマを一度に1セッションだけが触るルール**
   - migration の番号衝突が一度も起きなかった。
   - 本番 D1 への適用を「`main` のマージ前に指揮役が行う」と決めていたので、リリース時の手順も迷わなかった。
4. **指揮役による、並行 PR をまとめた試しマージ**
   - 同時に終わった PR をまとめて試しにマージし、全チェックを回してから順に取り込んだ。
   - #25 と #26 の衝突は、マージ前に見つけて作業セッションに解消してもらえた。
5. **報告の型（「判断してほしいこと」＋おすすめ）**
   - 作業セッションが「判断してほしいこと」をおすすめつきで返し、指揮役がそれを1つの質問にまとめた。そのため、オーナーの仕事はほぼ「決めるだけ」になった。
6. **実装を見ていないサブエージェントにテストを書かせる（S3）**
   - 期日計算のテストを、docs の境界ルールだけを渡したサブエージェントに書かせた。実装の思い込みがテストに入るのを防げた。

## 問題だったことと、次の対策

| # | 問題 | 起きたこと | 次の対策 |
|---|---|---|---|
| 1 | **報告の中継がオーナー頼み** | 完了報告は毎回オーナーが貼り付けて中継した。起動もチップのクリック待ち。全体の速度はオーナーの応答待ちで決まっていた | 作業セッションの完了時に、指揮役へ直接報告させる（`SendMessage`。S7 では実際に使えた）。指揮役は `gh pr list` で新しい PR を拾う。オーナーには判断だけを回す |
| 2 | **最後の一歩が権限で止まった** | 本番 D1 の読み取りと、シークレットの書き込み（VAPID 鍵）が、自動モードの権限判定で止まった。リリースの最後の作業がオーナーに戻った | 着手前に「Claude にやらせる本番操作」と「オーナーがやる操作」を決める。前者は `.claude/settings.json` の許可ルールに、具体的なコマンドの形で入れておく |
| 3 | **本番でしか起きない挙動の発見が遅い** | `development` には検証環境がなかった。Workers 固有の挙動は、リリース直前やプレビュー（wrangler dev）で個別に見つかった（`caches.default`、Assets の `.html` リダイレクト、`cf-connecting-ip`、ビルド時のフォント取得など）。87コミットを一度にリリースした | `development` への push で、検証用の Worker（例: `zumi-web-staging` と別の D1）に自動デプロイする。リリースは、検証環境での確認を経た小さな単位にする |
| 4 | **共有モジュールの持ち主が決まっていなかった** | 今日タブ・振り返り・通知を並行で作った結果、期日計算の入力を読むクエリが3か所に重複した。後から Q5 で共通化した。日付の整形関数の置き場所も同じ構図だった | 分割表に「共有するモジュールとその持ち主」の列を足す。土台のセッション（S1）で、データ読み込みの関数の形（引数と戻り値）まで決めておく |
| 5 | **同じマシンで並行させすぎた** | 4セッションが同時に build・test・E2E を回すと load average が18（8コア）に達した。DB テストがときどきタイムアウトし、3つのセッションが同じ症状を報告した | 同時に動かす作業セッションは2〜3本にする。重い確認は CI に任せる。クラウドのセッションに逃がすのも手 |
| 6 | **開発環境の決めごとが後追い** | lockfile は npm のバージョン差で全体が書き換わった（npm@10.9.7 に固定した）。worktree ごとの dev サーバーは Cookie が衝突した（`*.localhost` の規則を作った）。prettier・`format:check`・E2E は最後に入れた | プロジェクトの最初に入れておく: `packageManager` での npm 固定、dev サーバーのホスト名の規則、`format:check`、E2E の骨組み（ログインできるところまで）、PR 監視の紐付けの確認 |
| 7 | **UI の解釈の判断が完了報告まで出てこない** | S6・S9・S10 は、モックと docs の食い違いを実装後にまとめて報告した。結果は「おすすめで」が多く、そのまま採用されることがほとんどだった | 方針を事前に決める。docs の意図とモックで決まる判断は、作業セッションが決めて PR に記録する。オーナーに回すのは、プロダクトの方向・法務・お金・本番データに関わるものだけにする |
| 8 | **作業セッションから PR を見張れない** | 複数のセッションで「PR を紐付けられなかった」と報告があった。CI は指揮役が `gh` で見るしかなかった | 着手前に1回、PR 監視が使えるか（リポジトリが認識されるか）を確かめる。使えないなら、CI の確認は指揮役の担当と決めておく |
| 9 | **終わった worktree が残る** | 終わったセッションの worktree が `.claude/worktrees/` に溜まった | マージ後の片付けを、指揮役の手順に入れる |

## 次に自律的に進めるときの進め方

### サブエージェントとサブセッションの使い分け

今回の規模（1機能で数十分〜数時間、画面確認・PR・レビューを伴う）なら、**実装の単位は今回どおりサブセッション（別セッション＋worktree＋PR）が適切**だと考える。

| 手段 | 向いている仕事 | 向かない理由・注意 |
|---|---|---|
| **サブセッション**（`spawn_task` で起動する作業セッション） | 1機能＝1ブランチ＝1PR の実装。ブラウザでの確認、`/code-review`、長い試行錯誤 | 起動にオーナーのクリックが要る。報告の中継を自動化しないと、オーナーが律速になる |
| **サブエージェント**（`Agent` ツール。`isolation: "worktree"` も可） | 範囲の狭い調べもの（モックの読み取り）、実装を見ないテストの作成、独立したレビュー（第二の目）、指揮役の確認作業の肩代わり | 結果は要約で返るので、長い実装では途中の判断が見えない。指揮役のセッションで動くため、並べすぎると指揮役のコンテキストとマシンを圧迫する |
| **Workflow**（オーナーが明示的に頼んだとき） | 決まった型の一斉処理。複数の観点からのレビューとその検証、全画面の見た目チェックなど | トークンを大量に使う。実装の本体より、検証の手間を減らすのに向く |

**判断の目安:**
- 成果物が PR で、人が後から読み返すもの → サブセッション
- 答えだけが欲しく、指揮役が次の判断に使うもの → サブエージェント
- 同じ型の確認を何十回も回すもの → Workflow

### 自律度を上げる段取り

**1. 設計の段階（オーナー＋Claude）で用意するもの**
- 理由つきの要件 docs、画面モック
- 分割表: セッション、着手条件、触る範囲、共有モジュールの持ち主、スキーマの担当、推奨エフォート
- 判断の権限表: 作業セッションが決めてよいこと／指揮役が決めてよいこと／オーナーに回すこと
- 権限の事前設定: 本番 D1 の migration 適用、検証環境へのデプロイ、PR のマージは許可しておく。本番のシークレットと課金に関わる操作はオーナーの作業として明記する
- 基盤: CI（lint・typecheck・test・format・E2E の骨組み）、検証環境、パッケージマネージャーの固定、dev サーバーの規則

**2. 実装の段階（指揮役が回す）**
- 起動プロンプトは、今回の型（担当名、読む docs、スコープと触らない範囲、完了条件、推奨エフォート、報告に書くこと）を使う
- 完了報告は、作業セッションから指揮役へ `SendMessage` で直接送らせる
- 指揮役は PR のレビュー、試しマージ、全チェック、`development` へのマージ、docs への記録まで行う
- 権限表で指揮役が決めてよい判断は、指揮役が決めて docs に記録する。オーナーには後でまとめて見せる
- オーナーに回すのは、権限表の「オーナーに回すこと」と、リリースの承認だけにする

**3. リリースの段階**
- 検証環境で確認したものを、区切りのよい単位で `main` へ出す
- 本番でしか確かめられないこと（実機、オーナーのアカウントでの確認）は、リリースのたびに一覧にしてオーナーに渡す

### このリポジトリで次にやると効くこと

- `development` の検証環境（Worker と D1 を別に用意）への自動デプロイ
- `package.json` の `packageManager` で npm のバージョンを固定する
- `.claude/settings.json` の許可ルールを整える（本番 D1 の読み取りと migration、検証環境へのデプロイ）
- CLAUDE.md の「セッション運用」に、「判断の権限表」と「完了報告は `SendMessage` で指揮役へ」を足す
- 終わった worktree の片付け

> 関連: [用語定義](./01-glossary.md) / [通知](./02-notifications.md) / [画面構成](./04-screens.md) / [技術スタック・DBスキーマ](./05-tech-stack.md)

## 3-2. Duty 管理

### 属性

| 属性 | 型 | 説明 |
|---|---|---|
| `name` | String | 自由入力。テンプレートから作成した場合は初期値あり |
| `icon` | String | プリセットから選択。値は lucide のアイコン名（例: `trash-2`）。絵文字は使わない（後述） |
| `scheduleType` | Enum | 下記6種 |
| `scheduleConfig` | Json | タイプに応じた設定値 |
| `notifyPrevNight` | Boolean | 前夜通知の有無 |
| `noteEnabled` | Boolean | 記録時にメモ欄を出すか。デフォルト false |
| `sortOrder` | Int | DnD で手動設定 |
| `status` | Enum | ACTIVE / PAUSED / ARCHIVED |

**アイコンを絵文字にしない理由**: シェア画像を Satori（`next/og`）で生成する際、絵文字は外部の絵文字画像に頼ることになり、端末上の見た目とも一致しない。シェア画像がプロダクトの主要な獲得導線である以上、ここは確実に描画できるプリセットアイコンに倒す。また、モック・LP の単色の線アイコンと揃え、「朱色一色・事務的なトーン」（[デザイン方針](./00-overview.md#デザイン方針)）を保つ。

通知本文に絵文字を入れる目的で絵文字アイコンを採用する案も検討したが、不採用とした（2026/11）。通知は展開前に2行程度しか見えず、絵文字の有無で読みやすさがほとんど変わらないため（通知の文面は [通知](./02-notifications.md#通知の文面) を参照）。

**プリセットアイコン**: lucide（`lucide-react`）から生活系のアイコンを16〜24個選び、`packages/types` に定数として定義する。DB にはアイコン名をそのまま保存する。Web アプリでもシェア画像でも同じ SVG を描画する。

**status を3値にする理由**: 旅行・入院・繁忙期などで一時的にできない期間を「未達」として積み上げないため。PAUSED 中は通知対象からも達成率の分母からも外れる。

**一時停止・アーカイブの履歴**: 現在の `status` だけを持つと、一時停止を解除した時点で過去の週の分母が変わってしまう。これを避けるため、一時停止の期間を `duty_pauses`（`dutyId`, `startDate`, `endDate`）として記録する。再開前は `endDate` が null。あわせて `duties.archivedAt` を持つ。過去の週の達成率もログと期間から導出し、スナップショットは持たない。遡り記録をした場合も、そのまま過去の週に反映される。

**`dueTime`（時刻指定）は v1 では持たない**: 完了フロー自体には関与せず、期限切れ表示・ソート順という「あると便利」レベルの用途にとどまっていた。「朝では間に合わない」というニーズはすでに `notifyPrevNight` でカバーできているため、時刻管理は不要と判断した。「1タップで済」を掲げる以上、登録フォームの入力項目は増やす方向より減らす方向を優先する。時刻指定の需要が実際に確認できた場合は、v2でオプトインの詳細設定として追加する。

### 繰り返しタイプ

| タイプ | `scheduleConfig` | 期日の決まり方 | 用途例 |
|---|---|---|---|
| `DAILY` | `{}` | 毎日 | プロテイン、歯磨き |
| `WEEKDAYS` | `{ "weekdays": [2, 5] }` | 曜日固定（複数可） | ゴミ出し（火・金） |
| `NTH_WEEK` | `{ "weekdays": [3], "every": 2, "anchor": "2026-08-05" }` | 隔週の曜日（v1 は `every` = 2 固定） | 隔週の資源ゴミ |
| `MONTHLY` | `{ "dayOfMonth": 27 }` または `{ "nth": 1, "weekday": 0 }` | 月次 | 家賃振込、防災用品の点検 |
| `WEEKLY_COUNT` | `{ "timesPerWeek": 1 }` | 決まらない（週内で消化） | 英語学習 |
| `SINCE_LAST` | `{ "days": 2 }` | 前回**完了**から N 日 | 風呂、シーツ交換 |

**`SINCE_LAST` が中核の差別化点。** 起点固定の「N日ごと」では、1回飛ばした時点で未達が溜まり続ける。前回完了を起点にすることで、2日空けても入った瞬間にそこからリセットされ、過去の失敗が追いかけてこない。風呂を「毎日」で管理すると毎日未達が積み上がって心が折れるが、この型なら実態に合い、達成率も破綻しない。

### 期日計算の境界ルール（2026/11 確定）

`packages/types` の期日計算（web/notify 共通）は以下に従う。

| 項目 | ルール | 理由 |
|---|---|---|
| 1日の区切り | ユーザーのタイムゾーンの0時 | 深夜に前日分をつけるケースは、詳細モーダルの対象日変更と過去日表示で対応できるため |
| 週の区切り | ユーザー設定の「週の始まり」（月曜 / 日曜。初期値は月曜） | 週N回・達成率・週次サマリーはすべてこの区切りで集計する。設定を変えた場合、過去の週も新しい区切りで再計算する |
| `MONTHLY` の日付指定 | 29〜31日を指定し、その月に該当日がなければ月末に丸める | 「31日に家賃」のような指定で、短い月だけ期日が消えるのを防ぐ |
| `MONTHLY` の第N曜日 | `nth` は 1〜4 と「最終」（`-1`）のみ | 第5曜日は月によって存在しないため |
| `NTH_WEEK` | `every` は 2（隔週）に固定。UI は「隔週にする」のみ | 3週ごと以上のユースケースが薄く、UI を単純に保つため |
| `NTH_WEEK` の数え方 | `anchor` を含む週（ユーザーの「週の始まり」で区切る）を1週目とし、そこから偶数週後の週の `weekdays` を期日にする。`anchor` より前の日は、同じ週でも期日にしない | 隔週の月・木のような複数曜日を同じ週にまとめるため、7日ブロックではなく暦の週で数える。そのため週の始まりを変えると、日曜を含む複数曜日の隔週だけは対象週がずれうるが、設定を変えることはまれなので許容する。起点日として選ばせている以上、それより前に期日は出さない |
| 期日確定型の取りこぼし | 期日を過ぎても翌日に持ち越さない。その日の未達として残る | 持ち越すと「今日」が過去の未達で埋まり、ストリーク型の失敗パターンに戻るため。遡り記録で後から済にできる |
| `SINCE_LAST` の初回 | DONE のログが1件もなければ、作成直後から「そろそろ」に出す | 初回の押印をすぐ体験でき、その記録が以後の起点になるため |
| `SINCE_LAST` の催促の境界 | 前回の DONE から `days` 日以上経った日から「そろそろ」に出す（`days: 2` で月曜に済 → 水曜から）。SKIP は起点にしない。一時停止中に付いた DONE は起点に使う | 「前回**完了**から N 日」のため。一時停止明けは、前回の DONE からの経過日数しだいで、すぐ「そろそろ」に出ることがある |
| `WEEKLY_COUNT` の週の目標回数 | `min(timesPerWeek, 週内の有効日数)` とする。作成した週は作成日から週末まで、一時停止・アーカイブで日が欠けた週はその分だけ有効日数が減る。済の数は目標回数で頭打ちにする（達成率は100%まで） | 週の途中で作った・止めただけで未達扱いになるのを防ぐため。作成週だけの例外を、一時停止・アーカイブにも同じ考え方で広げた |
| 当日のログの扱い | 今日タブのセクション（今日／そろそろ／今週）と `WEEKLY_COUNT` の残回数は、当日のログより前の状態で決める。当日に済ませたものは同じセクションのまま「済んだもの」に移る | 押印した瞬間に Duty が別のセクションへ移ったり消えたりしないようにするため |
| 有効期間 | 作成日は当日から対象。アーカイブした日は当日から対象外（`archivedAt` をユーザーのタイムゾーンで日付にする）。一時停止期間は `duty_pauses` の `[startDate, endDate)` の半開区間で、`startDate`（一時停止した日）から対象外、`endDate`（再開した日）から通常どおり | 押した日をそのまま記録でき、期間の端の1日ずれの解釈が生まれないため |
| 一時停止・アーカイブの判定元 | `duties.status` ではなく、`duty_pauses` と `archivedAt` から判定する。状態を変えるときは、この2つも必ず書く | 過去の週を再計算しても結果が変わらないようにするため（`status` は現在の状態しか持たない） |
| 次の期日のプレビュー | 期日確定型は当日のログを見ず、当日が期日なら済ませた後も当日を返す。済ませた当日を出したくない画面は、呼び出し側で翌日から探す | 期日の計算と記録の状態を分け、関数を単純に保つため |

### 繰り返しタイプの選択UI（自由入力時）

6タイプをそのまま横並びで見せると、テンプレートを使わない自由入力ユーザーが確実に離脱する。テンプレートで大半のケースを吸収する前提のもと、自由入力に到達したユーザーに対しては2段階の絞り込みで案内する。

**第1段階（ユーザーの言葉で聞く）**

| 選択肢 | 対応するタイプ |
|---|---|
| 毎日やる | `DAILY` |
| 曜日が決まっている | `WEEKDAYS`（詳細設定で「隔週にする」を選ぶと `NTH_WEEK`） |
| 毎月やる | `MONTHLY` |
| 週に何回か（曜日は気分次第） | `WEEKLY_COUNT` |
| 前回やってから◯日空いたら | `SINCE_LAST` |

**第2段階（詳細設定）**

- 曜日選択: カレンダーの曜日を並べたトグルUI。「隔週にする」を選んだ場合のみ起点日（`anchor`）の選択が追加で出る（`every` は2固定）
- 毎月: 日付指定 or 「第N◯曜日」の切り替え（第1〜4・最終）
- 週◯回: 回数のステッパー
- ◯日空いたら: 日数のステッパー

**共通仕様**: 設定内容に応じて「次の期日: 8/26（水）」「あと1回・日曜まで」のように、次回の期日をリアルタイムでプレビュー表示する。設定結果を都度言語化することで、ユーザーが自分で設定ミスに気づける状態を作る。実装コストに対して離脱防止の効果が大きいため、フェーズ2（Duty CRUD）の中で優先的に組み込む。

### テンプレート（2026/11 確定）

テンプレートは `packages/types` にコード定数として定義する（DB には持たない）。各テンプレートは「名前・アイコン・繰り返しタイプ・初期設定」を持つ。テンプレートから作った Duty は通常の Duty と区別しない（`templateId` は保存しない）。

| # | 名前 | アイコン（lucide） | タイプ | 初期設定 |
|---|---|---|---|---|
| 1 | ゴミ出し | `trash-2` | `WEEKDAYS` | 曜日は未選択（入力必須） |
| 2 | お風呂 | `bath` | `SINCE_LAST` | 2日 |
| 3 | プロテイン | `cup-soda` | `DAILY` | — |
| 4 | サプリ | `pill` | `DAILY` | — |
| 5 | 英語学習 | `book-open` | `WEEKLY_COUNT` | 週2回 |
| 6 | シーツ交換 | `bed-double` | `SINCE_LAST` | 14日 |
| 7 | 水回り掃除 | `shower-head` | `SINCE_LAST` | 7日 |
| 8 | 掃除機がけ | `brush` | `SINCE_LAST` | 5日 |
| 9 | エアコンフィルター掃除 | `air-vent` | `MONTHLY` | 毎月1日 |
| 10 | 家族への連絡 | `phone` | `WEEKLY_COUNT` | 週1回 |

アイコン名は仮置き。フェーズ2でプリセット一覧を確定するときに見直す。

- **テンプレートを選んでも即登録はしない**: テンプレートをタップすると、内容が入った状態で Duty 追加シートが開く。ユーザーが確認・修正して「追加する」で確定する。ゴミ出しの曜日のように人によって違う設定があり、「選ぶだけで登録」は成立しないため
- **初期値を決められない設定は入力必須**: ゴミ出しの曜日のように、未入力のままでは「追加する」を押せない
- **同じテンプレートから何件でも追加できる**: ゴミ出しを「可燃（火・金）」「資源（隔週水）」のように分けて登録するケースのため
- 候補のうち、コンタクトレンズケース交換・常備薬の在庫確認・サブスクの見直し・観葉植物の管理は、利用者が限られるか自由入力で足りるため外した

### 記録操作

- 一覧からワンタップで完了（「済」の押印アニメーション）。**モーダルは開かない**
- 長押しで詳細モーダル → 対象日の変更・スキップ・メモ（`noteEnabled` 時のみ）
- 過去日への遡り記録（昨日の分を今朝つける、が最頻ユースケース）
- スキップ: 理由入力なしで「今日はやらない」を確定。夜の催促が止まる。達成率上は未達扱い
- 取り消し（誤タップのリカバリ）

### カスタムフィールドは実装しない

Habito で設計していた活動ごとの追加入力項目（TEXT / NUMBER / CHECKBOX、単位、必須フラグ）は ZUMI では採用しない。

- 記録モーダルに必須入力があると「1タップで済」が成立せず、LP の主訴求と正面から衝突する
- 「練習時間を測りたい」は計測・分析側の欲求であり、ZUMI の「1タップで済ませる」という守備範囲外
- DB 上も `CustomField` / `LogFieldValue` の2テーブルと動的レンダリングが不要になり、実装量が大きく減る

計測ニーズが確認できた場合は、v2 で「計測 Duty」という別カテゴリとして設計し直す。既存の Duty に後付けしない。

### 編集

- Duty の削除は原則アーカイブとし、過去ログは保持する
- 並び替え（DnD による手動。UI は v1.1）
- 繰り返しルールを編集した場合、過去の週の達成率も新しいルールで再計算する。ルールの変更履歴は持たない（頻度が低く、履歴を持つコストに見合わないため）

## 3-3. 記録（Log）

| 属性 | 型 | 説明 |
|---|---|---|
| `targetDate` | Date | どの「日」の記録か（深夜に前日分を記録するケース対応） |
| `loggedAt` | DateTime | 実際に操作した日時 |
| `status` | Enum | DONE / SKIP |
| `note` | String? | 任意テキスト。`noteEnabled` の Duty のみ |

**制約**: 1 Duty × 1対象日 = 1レコード（ユニーク制約）。`WEEKLY_COUNT` は週内の別日に複数回消化する形になるため、この制約と競合しない。

## 3-4. 振り返り・シェア

| 機能 | 内容 |
|---|---|
| 週次サマリー | 達成率（例: 18/20）、Duty ごとの内訳、前週との差分 |
| カレンダーヒートマップ | 月表示。日ごとの達成度合いを濃淡で表示 |
| シェア画像生成 | 週次サマリーを PNG カード化。保存・共有シートに送出 |
| 履歴閲覧 | 日付グループのリスト。Duty 名での絞り込み、無限スクロール |

### 達成率の分母

タイプごとに分母の定義が異なる。ここを揃えると期日不確定型が破綻する。

| タイプ | 分母 |
|---|---|
| 期日確定型（DAILY / WEEKDAYS / NTH_WEEK / MONTHLY） | 週内に到来した期日数 |
| `WEEKLY_COUNT` | `timesPerWeek`（作成週・一時停止・アーカイブで日が欠けた週は `min(timesPerWeek, 週内の有効日数)`。[境界ルール](#期日計算の境界ルール202611-確定)） |
| `SINCE_LAST` | 週内に発生した催促の回数 |

`SINCE_LAST` の催促回数は別テーブルを持たず、ログから導出する。週内の完了数に、週末時点で催促状態が継続していれば +1 する。日数を分母に取ると風呂が常に未達になり、この型を導入した意味が失われる。

PAUSED 期間（`duty_pauses`）および `archivedAt` 以降は分母に含めない。作成日より前も含めない。週の区切りはユーザー設定の「週の始まり」に従う（[期日計算の境界ルール](#期日計算の境界ルール202611-確定)）。

**分子と「週末時点」の扱い（2026/11 確定）**:

- 分子は、期日確定型では期日に付いた DONE だけを数える（期日でない日に対象日を変えて付けた DONE は数えない）。どのタイプも、一時停止期間・作成日より前・アーカイブ後の日の DONE は数えず、今日より後の日付のログも数えない
- `SINCE_LAST` の「週末時点」は、今週については今日の時点とする。今日まだ済ませていなければ、今日の催促も +1 に数える。その日が一時停止中・アーカイブ後なら +1 しない（止めている間に未達を積み上げないため）
- `SINCE_LAST` の完了数には、催促が発生する前に済ませた DONE も含める。毎日済ませれば 7/7 になる

### シェア画像の設計方針

- 未達を隠さない。満点だけを出せる設計にすると、そもそも投稿されない
- 絶対値ではなく前週比を主役に置き、達成率が低いユーザーでも投稿の口実を持てるようにする
- 「済」の朱印を主要ビジュアルとし、炎・ストリーク数字といった既存習慣アプリの記号を使わない。タイムライン上で一目で識別されることを狙う
- 朱印の角度をわずかにランダムにずらし、機械生成感を消す
- フッターにドメインを入れ、画像単体で流入導線として機能させる

**ストリーク（連続記録日数・最長記録）は表示しない。** コンセプトの根幹に関わるため、統計としても持たない。

**画像生成はスクリーンショットではなく専用生成（`next/og`）で行う。** 実画面をそのままキャプチャすると進捗バーやタブバーなどアプリUIがそのまま写り込み、SNS上で「広告として機能する洗練されたカード」になりにくい。専用生成であれば、SNS向けアスペクト比への固定、フッターへのドメイン焼き込み、朱印の角度をランダムにずらす演出などが実現できる。実装コストはあるが、獲得導線としての位置づけが強いためフェーズ6で後回しにしない。

**バリエーション案（A/Bテスト候補）**: 達成率の数字が前面に出ると「評価されている感」が強まり、自己啓発アプリ的なトーンに寄ってしまう懸念がある。現行案（前週比＋達成率＋朱印の並び）に加えて、**数字を出さず「済んだ朱印だけを並べたグリッド」に特化したバージョン**も候補として検討する。達成率は画面内の補助情報にとどめ、判子が並ぶビジュアルのみで完結させる案。v1では現行案（前週比を主役、未達を隠さない）で実装し、フェーズ6のタイミングで両案を比較検討する。

## 3-5. アカウント・オンボーディング

- メール／パスワードでサインアップ（better-auth）
- メール認証（サインアップ後に確認メールを送信し、認証完了までは利用を制限する）
- サインアップ時に利用規約・プライバシーポリシーへの同意を必須とする
- サインアップ直後にオンボーディング（後述の4ステップ）で初期設定を行う
- タイムゾーンをユーザーごとに保持（通知配信の前提）
- パスワードリセット（メール送信 → トークン検証 → 再設定）
- メールアドレス変更・パスワード変更・退会
- データエクスポート（JSON / CSV）

**メール認証を必須にする理由**: 通知（朝夜のまとめ・週次サマリー）や将来のメールフォールバックの配信先として使うため、到達可能なアドレスであることを早期に担保する。

**利用規約・プライバシーポリシーへの同意を必須にする理由**: アカウント作成時にユーザーデータ（メールアドレス、Duty/ログデータ、Sentryへのエラー送信データ等）を扱う以上、法的な同意取得をオンボーディングの入口に組み込む。規約・ポリシー自体の作成タスクは [09-implementation-tasks.md](./09-implementation-tasks.md) を参照。

### オンボーディング（2026/11 再設計）

当初は「テンプレートを複数チェックして確定ボタンで一括登録」を想定していた。しかしゴミ出しの曜日のように、テンプレートの初期値だけでは決まらない設定があるため、1件ずつ追加シートで確定する流れに再設計した。

| ステップ | 内容 |
|---|---|
| 1. やることを選ぶ | テンプレート一覧（2列のカード）。カードをタップすると、内容が入った状態で Duty 追加シートが開く。「追加する」で一覧に戻り、追加済みのカードに「済」の印が付く。同じカードを再度タップすると、もう1件追加できる。「自由に追加する」は空のシートを開く。下部のボタンは「次へ（N件）」で、0件のときは「あとで追加する」 |
| 2. 通知の時刻 | 朝（初期値 7:30）・夜（初期値 22:00）・週次サマリーの時刻（初期値 20:00）、週の始まり（初期値 月曜）。タイムゾーンはブラウザから自動取得 |
| 3. ホーム画面に追加 | iOS の Safari で、まだホーム画面アプリとして開いていない場合だけ表示する。手順は clipnote の案内（https://clipnote.paritto.dev/app ）にならう: 共有ボタン → 「ホーム画面に追加」 → 「Webアプリとして開く」をオンのまま「追加」。ホーム画面アプリでは再ログインが必要なことも案内する |
| 4. 通知の許可 | iOS 以外の環境、またはホーム画面アプリとして開いている場合に表示する。許可ボタンで Web Push を購読する |

- **すべてのステップを飛ばせる**: 初回の離脱を防ぐため
- **完了の判定**: `user_settings.onboardedAt` に記録する。ステップ2を終えるか飛ばした時点で記録し、以後 `/app` からオンボーディングへリダイレクトしない
- **通知が未許可のとき**: 今日タブの上部に許可を促すバナーを出す。iOS ではホーム画面アプリと Safari でログイン状態が共有されず、Safari 上のオンボーディングでは通知を許可できない。そのため iOS では、ホーム画面アプリで再ログインした後のこのバナーが、通知許可の実質的な入口になる
- **`user_settings` の作成**: サインアップ時に better-auth の `databaseHooks`（user 作成後）で行を作る。タイムゾーンは初期値 `Asia/Tokyo` で作り、オンボーディングやアプリを開いたときにブラウザの値で更新する。フェーズ3以降の「今日」の判定がタイムゾーンを前提にするため、オンボーディング（フェーズ7）を待たずにフェーズ2で実装する
- Duty タブからの通常の追加でも、同じレイアウトのテンプレート画面を使う（[画面構成](./04-screens.md#4-3-duty)）

**メール認証・パスワードリセット・法務ドキュメントはMVPスコープ（フェーズ1）に含める**。これらは後付けするとオンボーディングフローの手戻りが大きく、認証基盤に食い込むため、後回し候補（[07-roadmap.md](./07-roadmap.md) 参照）からは外している。

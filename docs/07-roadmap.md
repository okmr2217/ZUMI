## 7. 実装優先順位

### MVPスコープの考え方

MVPでは「コア機能（繰り返しタイプ6種）の網羅性」を優先軸に置く。6タイプ（`DAILY` / `WEEKDAYS` / `NTH_WEEK` / `MONTHLY` / `WEEKLY_COUNT` / `SINCE_LAST`）は削らずフルスコープで実装する。`NTH_WEEK`（隔週）は「隔週の資源ゴミ」のようなユースケースが外せないため維持する。

期日計算ロジックは6タイプ分をそのまま抱えるため、他フェーズ側で工数を捻出する形にスコープを再構成した。以下の機能はMVPでは実装せず、後続フェーズ（v1.1以降）に回す。

| 後回しにする機能 | 理由 |
|---|---|
| Duty の DnD 並び替え | 無料プランは Duty 5件までのため、作成順表示で当面代替可能。DB の `sortOrder` 列自体は維持し、UI側のみ後回し |
| 月次カレンダーヒートマップ | 獲得ループの本体は週次サマリー＋シェア画像であり、ヒートマップは補助機能のため分離 |
| 通知のメールフォールバック | まず Web Push のみで配信し、iOS制約（ホーム画面追加前提）の影響を見てから判断 |
| 前夜通知（Duty単位） | 朝夜の基本2通が安定してから、個別オプトインとして追加 |
| データエクスポート（JSON/CSV） | 初期ユーザー数を踏まえ優先度を下げる |
| メールアドレス変更 | 退会機能は維持するが、変更系機能は後回し |

これらは独立性が高く、後付けしても手戻りが少ない箇所を選んで削っている。一方で繰り返しタイプ6種の期日ロジックは今日タブ・通知の両方に食い込み後から追加しづらいため、削減対象から外した。

### フェーズ

| フェーズ | 内容 |
|---|---|
| 1 | 認証（better-auth + D1）、`packages/db` のスキーマとマイグレーション |
| 2 | Duty タブ（CRUD + 繰り返しタイプ6種の設定UI。DnD並び替えはMVP対象外、`sortOrder` は保持） |
| 3 | 今日タブ（期日計算ロジック + 3セクション + ワンタップ押印） |
| 4 | 通知（Service Worker + notify Worker の Cron。MVPは Web Push のみ、前夜通知は対象外） |
| 5 | 振り返りタブ（週次サマリー + 履歴リスト。月次ヒートマップはMVP対象外） |
| 6 | **シェア画像生成（`workers-og`）** ← 獲得導線なので後回しにしない |
| 7 | 設定モーダル、オンボーディングのテンプレート選択（データエクスポート・メールアドレス変更はMVP対象外） |
| 8 | LP |

フェーズ3の期日計算ロジックが実装上の山場。6タイプそれぞれの「今日が対象か」「催促が発生しているか」「週の残回数」を返す純粋関数として `packages/types` 側に切り出し、web と notify の双方から同じ実装を使う。ここがズレると「通知は来たのに画面に出ていない」が発生する。

**フェーズ8（LP）はフェーズ1完了後に着手する。** 表の番号は成果物の依存関係の目安であり、厳密な実施順ではない。LP はアプリ本体（フェーズ2〜7）に依存しないため、認証基盤が整った時点で並行して進めてよい。

### v1.1以降で追加する機能

- Duty の DnD 並び替え
- 月次カレンダーヒートマップ
- 通知のメールフォールバック
- 前夜通知（Duty単位）
- データエクスポート（JSON/CSV）
- メールアドレス変更
- 課金（Stripe等の決済連携・Proプラン制御）: MVPでは無料プランの制約ロジックのみ実装し、決済導線は持たない（[06-billing.md](./06-billing.md) 参照）
- Duty ごとの統計

各フェーズをタスクレベルまで分解したチェックリスト、および基盤構築（フェーズ0）・PWA対応・QA/リリース準備・法務ドキュメント作成など本ファイルに明記していない横断タスクは [09-implementation-tasks.md](./09-implementation-tasks.md) を参照。
